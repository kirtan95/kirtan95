# Dev Log

A daily engineering journal — short notes on things I'm learning and building.

## 2026-09-28

**RAG retrieval: chunking matters more than the embedding model.** Been working on a RAG knowledge assistant (FastAPI + pgvector). Swapping embedding models moved hit-rate a few points, but fixing chunk boundaries — keeping tables and lists intact instead of naive fixed-size splits — moved it far more. Lesson: retrieval quality is a data-plumbing problem first, a model problem second.

## 2026-09-29

**Streaming LLM tokens from FastAPI with SSE.** Wired up token streaming for a chat endpoint today using FastAPI's StreamingResponse with Server-Sent Events instead of blocking until the full completion. The trick is an async generator that iterates the model's token stream, yields `data: {chunk}` frames, and a client that consumes them with an EventSource. I learned to disable proxy buffering (`X-Accel-Buffering: no`) and flush headers immediately, otherwise the whole "stream" arrives in one batch. Also made the endpoint accept a `stopped` signal so the client can cancel mid-stream and the generator releases the model call. Latency to first token dropped from seconds to under a second in the UI, which changes how the app feels entirely.
## 2026-09-30

**Lean Docker images for FastAPI + ML services.** Reworked a Dockerfile for a FastAPI service that pulls in ML libraries, and the big win came from treating the image like a supply chain instead of a junk drawer. A multi-stage build compiles native dependencies in a builder stage and copies only the installed packages into a python-slim runtime stage, so build tools never ship to production. Ordering the Dockerfile so dependency installs happen before the code copy keeps those layers cached across deploys, which makes rebuilds noticeably faster during iteration. Running the container as a non-root user and pinning the base image digest closes two easy security holes. Lesson learned: most of a "heavy ML image" is build debris, not the app itself.

## 2026-10-01

**pgvector HNSW: ef_search is the dial that matters.** Been tuning vector search in my RAG service (pgvector on Postgres). I already had an HNSW index built with m=16 and ef_construction=64, but recall versus latency still felt off. Turns out the build-time parameters matter far less than ef_search at query time - raising it from 40 to 100 lifted recall noticeably while keeping p95 latency comfortably in budget. The cleaner fix was setting it per-session with `SET hnsw.ef_search` instead of hardcoding it in the query, so I can tune it without redeploying. Lesson: index build params are set-and-forget, but ef_search is a runtime knob worth benchmarking against a golden question set.

## 2026-10-02

**Slack bots: ack fast, verify signatures, dedupe events.** Been wiring up a Slack bot and the two things that bite hardest are the 3-second ack window and duplicate event delivery. Slack retries a webhook if you don't ack in time, so every handler should ack first and hand off the real work to a background task, never do it inside the request. Every request also needs signature verification against the signing secret using the timestamp header, with a short expiry check to block replay attacks. And since retries can still deliver the same event twice, I keep a table of processed event_ids with a unique constraint so a duplicate insert just no-ops. Pattern: verify, ack, dedupe, then act. Boring plumbing, but it's what separates a demo bot from one that survives a busy channel.

## 2026-10-03

**Tool-calling safety: validate the arguments before the tool ever runs.** I have been adding function-calling to my agent workflow and the habit that has saved me the most grief is parsing the model's JSON arguments through a Pydantic model before dispatching. LLMs will happily return `{"count": "five"}` or invent parameters the tool doesn't accept, and a loose `**kwargs` pass-through turns those hallucinations into real bugs. So each tool now declares a strict schema, the dispatcher validates against it, and anything that fails gets re-asked to the model with the validation error included in the message. The bonus is that the same schema renders the tool descriptions for the API and the docs, so they can't drift apart. Small layer, but it is the difference between an agent that occasionally breaks and one that degrades gracefully.

## 2026-10-04

**WebSocket backpressure: stop buffering, start pushing back.** I hit a nasty failure mode in a Node.js WebSocket server under load: when a slow client cannot keep up, the server's per-socket send queue grows unbounded and eventually OOMs the process. The fix is `ws.bufferedAmount` - before each send, check whether buffered bytes exceed a threshold and, if so, either drop the message (for ephemeral game-state updates that will be superseded) or throttle that client. Better still, don't let clients subscribe to firehose updates they can't consume; batch state diffs on the server tick and send one compact snapshot per tick instead. Lesson: backpressure is a protocol design problem, not a bandwidth one - the server must decide what to do when the pipe is full, because silently buffering is just choosing to crash later.
## 2026-10-05

**React dashboards: downsample before you render, not after.** Been building a metrics dashboard in React with Chart.js and hit the wall where 50k time-series points turn the UI to molasses. Pagination helped the table but not the chart, so I switched to downsampling server-side with the Largest-Triangle-Three-Buckets algorithm before the payload ever reaches the client. The chart keeps its visual shape, payloads shrink by 95%+, and the raw points stay in Postgres for the drill-down view. I also moved the chart into a memoized component keyed on the data hash so unrelated state updates stop triggering full re-renders. Lesson: the browser is a display device, not a compute device — do the heavy lifting in Python, ship the pixels to React.

## 2026-10-06

**Idempotent pipelines: make every write safe to retry.** I have been hardening a Python ingestion pipeline that pulls records from an API and writes them to Postgres, and the failure I kept hitting was the duplicate-write-on-retry: a worker times out, the orchestrator retries, and suddenly there are two rows for one event. The fix that actually held was giving every record a stable natural key and writing with `INSERT ... ON CONFLICT (source, external_id) DO UPDATE SET ...`, so a retry is just a no-op instead of a data corruption event. On top of that I wrapped each batch in an explicit transaction and record a checkpoint cursor only after the commit succeeds, so a crash replays from the last good cursor rather than from somewhere in the middle. The lesson that stuck: retries are inevitable in distributed pipelines, so idempotency has to be a property of the write path, not something you bolt on later.

## 2026-10-07

**asyncpg pool sizing: size the pool like a budget.** I was tuning a FastAPI service against Postgres and kept hitting `too many clients already` under load. The fix was creating one `asyncpg` pool in the app lifespan (`min_size=5, max_size=20`) and sharing it everywhere, instead of opening a connection per request. My rule of thumb now: pool max should be roughly uvicorn workers times connections each can hold, staying well under Postgres `max_connections` with headroom left for admin work and migrations. I also set `command_timeout` on the pool so a stuck query gives its connection back instead of starving everyone. The lesson that stuck: a connection pool is a backpressure device, not a performance feature. Sizing it is deciding how many concurrent writers you are willing to fund.

## 2026-10-08

**MCP tool servers: an agent's tools are just a JSON-RPC API.** I have been packaging some of my agent workflow tools (search, file read, database queries) as an MCP server so any MCP-capable client can call them over stdio. The protocol is plain JSON-RPC 2.0: the client lists available tools, then sends `tools/call` with the tool name and arguments, and the server responds with result content. The habit that paid off was giving every tool a strict input schema and a hard timeout - one slow tool without a timeout stalls the whole agent loop, and MCP clients trust the schema you declare. The second lesson: return structured data (JSON strings) instead of prose, because the model parses JSON far more reliably than it summarizes a paragraph. It is the same discipline as my function-calling validation work, just moved to the transport layer - and it means the same tools work in Claude Desktop, my own agent, or anything else that speaks MCP.

## 2026-10-09

**Slack bots: ack first, think later.** While wiring up a slash command for a small ops bot with slack-bolt (Python, async app), I learned Slack re-delivers the request if it does not get an `ack()` within 3 seconds, so slow handlers end up firing twice. The handler now acknowledges immediately and pushes the slow work - the LLM call, the database lookup - into a background task, then updates the message later with `response_url`. I also verify the signing secret on every request so the endpoint cannot be hit by anyone who guesses the URL. The pattern generalizes to any webhook: accept fast, do the real work after you have already answered. Kept the bot single-purpose instead of a grab bag of commands, which also kept the scope honest.

## 2026-10-10

**Hybrid search: keyword precision plus vector recall, fused with RRF.** In my RAG service (Postgres + pgvector) I kept seeing pure vector search miss exact terms like product codes and error names, while plain full-text search missed paraphrases of the same idea. So I now run both for every query: `to_tsvector`/`tsquery` for keyword matching alongside the HNSW index for semantic recall, then fuse the two rankings with Reciprocal Rank Fusion so neither score scale can dominate. The fusion is just a SQL expression over two ranked subqueries, so it lives entirely in Postgres with no extra service to run. On my golden-question eval, recall improved without touching a single embedding, because the two retrievers fail on different questions. Lesson: hybrid search is not two systems bolted together, it is admitting one signal is never enough.

## 2026-10-11

**Structured LLM output: validate it like any other API response.** I stopped trusting raw model text in a FastAPI endpoint that asks an LLM to extract entities from support tickets and now require JSON mode, then parse the result into a Pydantic model. The model schema doubles as the contract: if the LLM drops a field or emits the wrong type, validation fails and I retry with a correction prompt instead of saving garbage to Postgres. Wrapping the retry in a bounded loop (max 2 retries) keeps costs and latency predictable instead of letting a confused model spin forever. Lesson: treat model output like user input - schema-first, validate-everything.

## 2026-10-12

**FastAPI BackgroundTasks is a convenience, not a job system.** I was auditing how embedding jobs get kicked off after a doc upload and realized BackgroundTasks runs after the response is sent but lives in the same worker process: if the process restarts or gets OOM-killed mid-task, the job silently vanishes. That is fine for fire-and-forget side effects like a webhook ping, but not for anything that must complete. The fix that actually holds up at my scale is a durable queue: insert the job into a Postgres table, then let a separate worker drain it with `SELECT ... FOR UPDATE SKIP LOCKED`, retries, and a dead-letter column. Now the web process never does real work — it validates, enqueues, and responds fast. Lesson: the moment a task must survive a deploy, it needs a queue; BackgroundTasks is just for work you are willing to lose.

## 2026-10-13

**FastAPI dependencies are how you keep an endpoint testable without a live database.** I finally stopped importing my session factory directly inside route handlers and started declaring everything as `Depends(get_db)` and `Depends(get_current_user)`. In tests I use `app.dependency_overrides` to swap in a per-test transaction-scoped session, so each test gets a clean database with zero mocking of internals. The rule I am settling on: any dependency that touches the network or the database gets an override in tests, everything else stays. The bonus I did not expect: I can now inject a failing dependency per test and assert my 500 handling and retry logic end to end. Lesson: if a test has to patch a module-level import to run, the endpoint was never decoupled, and DI is the decoupling.

## 2026-10-14

**LLM prompt caching: hash the prompt, check Redis, skip the model call.** I've been adding a plain exact-match prompt cache in front of my LLM endpoints: normalize the prompt (strip whitespace, sort any JSON keys), SHA-256 it, and look it up in Redis with a short TTL before ever calling the model. Cache hits return in single-digit milliseconds instead of seconds, which changes how repeated classification and summarization workloads feel. My rule: cache only deterministic prompts (temperature 0, no user-specific data baked in), and version the cache key with the model name and prompt template hash so a redeployed prompt can never serve stale output. Simple, boring, and one of the highest-ROI optimizations in my LLM tooling belt.

## 2026-10-15

**Docker Compose healthchecks: `depends_on` alone doesn't wait for readiness.** I kept hitting race conditions where my FastAPI container booted before Postgres was actually accepting connections, even with `depends_on` in place. The real fix was a healthcheck on the db service - `pg_isready` in `test`, with a `start_period` long enough for pgvector's slow first-boot index build - and `depends_on: {db: {condition: service_healthy}}`. Also learned that `interval` and `retries` on the healthcheck directly control how fast Compose declares the container up, so I tune them loose for cold starts and tight for the dev loop. The app still retries its connection pool on startup too, because health is a signal, not a guarantee - a database restart can still beat the app to the port. Lesson: ordering isn't readiness; always gate on an actual health probe.

## 2026-10-16

**Cross-encoder reranking: let the cheap model retrieve, the picky model rank.** My hybrid search in Postgres (tsvector plus pgvector HNSW, fused with RRF) pulled decent candidates, but the top slot still felt wrong a little too often for questions with overlapping vocabulary. So I added a second stage: take the top 40 candidates and rescore them with a small cross-encoder model that reads the query and passage together, then keep the top 5 for the LLM. Retrieval is about recall and can afford a bi-encoder; ranking is about precision and deserves the model that actually sees the pair. I run reranking in-process on CPU in a batched call so it adds about 100ms, which disappears against the LLM's own latency. The pattern is simple but it took me a while to accept: two stages beat one clever stage, because retrieval and ranking are different jobs.

## 2026-10-17

**Correlation IDs: trace one request from FastAPI to the Postgres worker.** Debugging a flaky embedding pipeline got painful because the FastAPI request log, the LLM call log, and the worker log all spoke different languages. So I now generate one UUID per incoming request in middleware, stash it in a `contextvars.ContextVar`, and have my structured logger inject it into every record with no argument threading. The worker picks the same ID up from the job row in Postgres, so a single query shows the request and all of its downstream work as one story. The asyncio caveat I learned the hard way: a `ContextVar` does not cross into `run_in_executor` threadpool jobs, so I pass the ID explicitly there instead of assuming it propagates. Lesson: one shared ID beats grep across three services, and it costs about fifteen lines of middleware.

## 2026-10-18

**Alembic migrations and pgvector indexes don't mix without some care.** I learned this one the hard way when an autogenerated migration tried to recreate my vector index on a table with a million embeddings and the deploy timed out. The problem: Alembic's autogenerate sees the HNSW index and wants to diff it, and `CREATE INDEX` without `CONCURRENTLY` takes a write lock for the full build. Now I write vector index migrations by hand: `CREATE INDEX CONCURRENTLY` inside a migration that runs outside a transaction (PostgreSQL forbids CONCURRENTLY in one), and I exclude the vector index from autogenerate with `include_object` so routine migrations don't touch it. Bonus detail I forgot twice: pgvector index creation needs the extension installed first, so the migration that enables `CREATE EXTENSION vector` has to be a dependency of any migration that builds on it. Lesson: ORMs autogenerate tables well and indexes badly - own your index migrations.

## 2026-10-20

**Postgres LISTEN/NOTIFY: stop polling your own pipeline.** I had an ingestion pipeline where a worker polled a `jobs` table every few seconds looking for new rows, and under load the polling queries themselves became a bottleneck. Switching the producer to run `NOTIFY new_job, '<id>'` after each insert, with the worker `LISTEN`ing on that channel, dropped notification latency to milliseconds with zero polling traffic. Two catches I had to handle: NOTIFY payloads are capped at 8000 bytes, so I only send the row id and re-fetch the row on receipt, and notifications are only delivered at transaction commit, which pairs naturally with insert-then-commit. I also kept a lightweight poller as a backstop for missed notifications, because a LISTEN connection can drop silently and nobody tells you. Lesson: Postgres already ships a pub/sub primitive - use it before bolting on Redis or a queue for simple in-database pipelines.

## 2026-10-21

**Prompt caching: stop paying full price for your system prompt.** I added prompt caching to an LLM tool-calling loop that sends the same long system prompt plus tool definitions on every turn, and the effect on a multi-turn session was immediate. The mechanics matter: you mark a cache breakpoint after the stable prefix, and as long as that prefix byte-matches on the next request, the provider skips recomputation and charges a fraction of the price. I learned to put everything static first - system instructions, tool schemas, few-shot examples - and push the user message and fresh tool results after the breakpoint, because one changed byte at the top invalidates the whole cache. One catch worth knowing: cached tokens still count toward the model's context limit, so this saves money and latency, not context window. Lesson: for any agentic loop that re-sends the same preamble, caching is the cheapest latency win on the table - no model swap required.

## 2026-10-22

**PostgreSQL partial indexes: index only the rows you actually query.** I've been tuning a hot query in my FastAPI service backed by PostgreSQL, and it only ever scans rows where `deleted_at IS NULL` and `status = 'active'` — a small slice of a large table. A partial index like `CREATE INDEX ... ON documents (tenant_id) WHERE deleted_at IS NULL AND status = 'active'` covers exactly that slice, so the index stays small enough to live in memory while writes to the rest of the table stop paying index-maintenance tax. The planner picks it up automatically as long as the query's WHERE clause implies the predicate. My rule of thumb now: if every query against a table shares the same predicate, that predicate belongs in the index. It's one of the cheapest query-speed wins in Postgres and I reach for it before considering read replicas or cache layers.

## 2026-10-23

**React search inputs: the useEffect cleanup is the concurrency model.** I have a search box that hits my RAG API as you type, and without cleanup the requests race — a slow response for "emb" renders over the fresh results for "embedding chunk". The fix is to create an `AbortController` in the effect, pass its signal to `fetch`, and return `controller.abort()` as the cleanup function, swallowing the `AbortError` in the catch. Combined with a debounce on the query state so I am not firing per keystroke, stale responses just disappear instead of needing version counters. Lesson that stuck: in React, effect cleanup is not hygiene, it is how you cancel async work — if the effect starts something, it has to know how to stop it.

## 2026-10-24

**WebSocket heartbeats: a silent client is not a connected client.** I have been working on a Node.js WebSocket room where players can idle on a flaky mobile connection, and the server kept treating dead sockets as live players because TCP alone never told it otherwise. The fix is a heartbeat: the server sends a ping every 30 seconds, marks each socket alive on pong, and terminates any socket that misses two in a row, which frees the seat and lets the room move on. I learned to clear the interval on close and to skip sending a ping to a socket that is still in CONNECTING state, because both mistakes leak timers or throw. Lesson that stuck: on a stateful connection, liveness is something you prove on a schedule, not something you assume from a handshake that happened minutes ago.

## 2026-10-25

**Node.js graceful shutdown: stop accepting, then drain, then exit.** I have been tightening up how my Node.js servers shut down, because the default behaviour on SIGTERM is to just die mid-request. The pattern I settled on is to first call `server.close()` so no new connections are accepted, then wait for in-flight requests and WebSocket messages to finish, with a hard timeout as a backstop so a single stuck client cannot hang the shutdown forever. I also close database pools and background timers in that same window, in reverse order of how they were started, so nothing tries to write after its connection is gone. One detail that caught me out: `server.close()` only waits for established connections, so long-lived WebSocket clients have to be tracked and closed explicitly or the process never exits. Lesson that stuck: shutdown is a feature with its own code path, not just the absence of startup, and it deserves the same care as the happy path.

## 2026-10-26

**Slack bots: acknowledge in three seconds, do the work later.** I hit this building a Slack slash command that kicked off a slow RAG lookup, and Slack kept showing users a timeout error even though the work eventually finished. The rule is strict: Slack expects an acknowledgement within three seconds of the request, or it retries and the user sees a failure. The fix was to split the handler in two: acknowledge immediately with a short "working on it" message, then run the slow lookup in a background task and post the real answer later with `response_url` or `chat.postMessage`. I also made the background job idempotent, because Slack retries a command it thinks timed out, and without a dedupe key the same question got answered twice. Lesson that stuck: for any chat bot, the acknowledgement is the contract and the answer is a follow-up, so never let model latency sit in the request path.

## 2026-10-27

**Postgres LISTEN/NOTIFY: push status updates instead of polling for them.** I have been looking at how to surface the status of a background data pipeline without a dashboard that polls the database every few seconds, and Postgres already has a built-in answer in LISTEN/NOTIFY. A worker sends NOTIFY on a channel when a job stage finishes, and any connected listener gets the payload immediately, so the UI updates on an event instead of on a timer. The catch I noted is that notifications are not queued for listeners that are disconnected, and payloads are size-capped, so they are a signalling mechanism rather than a job queue. The durable job row in the table stays the source of truth, and a listener that reconnects should re-read it before trusting anything it missed. Used that way, it removes a whole class of polling load for the price of a few lines of SQL.
